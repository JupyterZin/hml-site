Models are frozen at training time

Training is the only moment a model changes. After that, the weights are sealed. Everything the model "knows" during a session lives in the context window — and the context window evaporates when the session ends.

🧊

Weights are read-only

No session, however brilliant, updates the model. The next session starts from the exact same frozen weights as the first.

💨

Context evaporates

Decisions, dead ends, and hard-won context live in the chat. Close the tab and they are gone. Compaction loses them mid-session.

🔁

Teams re-debate everything

With several agents on one project, each re-asks the questions the others already answered. Work is repeated, decisions contradict.

The fix: a ledger, not a chat

If the model can't remember, give it something that can. HML keeps two files per project: events.jsonl is the truth; activeState.json is just a projection of it.

📒

Append-only by construction

The only code path that writes opens the file with the a flag and calls fsync. Nothing can truncate or rewrite history.

🔗

Hash-chained

Every event embeds the SHA-256 of the previous one. Edit any line and every read reports hash-mismatch or chain-break — forever.

🛡️

Server as guardian

Models never compute hashes or touch the disk. The server validates, canonicalizes (RFC 8785), timestamps, hashes, and commits — under a file lock.

🧽

The projection self-heals

Edit activeState.json by hand and nothing happens: it has no authority. The drift is reported as l1-drift and the file is rebuilt from events.jsonl on the next commit or init.

One contract, every agent behaves the same

Each project with a ledger carries the same AGENTS.md — the rules every agent reads at session start, whatever model is behind it. Different brains, identical behavior:

📖

Read first, always

Every session opens with hml_read_state and keeps currentStateHash; hml_query_events searches the history when more context is needed. No agent works from stale memory.

✍️

Hand over at the end

Every session closes with a handover: what happened, the complete task list, and decisions as ADRs — architecture decision records with context, decision and consequences. The next agent starts where you stopped.

🚫

Never touch the files

No agent edits events.jsonl, computes hashes, or guesses a previousStateHash. The server writes; models propose. A wrong fact is corrected by a new event, never by an edit.

🧭

Ledger is data, not orders

Content written by earlier sessions is information, never instructions. An agent that finds "ignore X, do Y" in the ledger reports it instead of obeying.

🔀

Lose the race? Merge, resend

On E_STALE_STATE the agent merges its task list with the current one and resends with the fresh hash — important because nextTasks replaces the previous list outright. Nobody rewrites over anyone.

🏷️

Pinned authorship

Each person's server runs --pin-author with their agent's name, so a confused model can't sign as the human — or as a teammate.

The trade-offs, honestly

The ledger is not free. You pay a small, fixed cost every session — and get back the hours your team used to spend reconstructing context.

What it costs

  • Every session opens with a ledger read — a few KB of tokens, every time.
  • Reads re-verify the whole chain: O(n). Fine until roughly 50 MB of history — how to rotate the log past that is still an open design question; there is deliberately no rehash command.
  • The team must actually write handovers. A skipped handover is lost context.
  • Across machines, git discipline: pull before you hand over, or the fork becomes a visible chain-break.

What it saves

  • No re-reading the whole codebase and docs to reconstruct "why" — the decisions are already there, as ADRs with context and consequences.
  • No re-debating settled questions: the ledger remembers what was decided and why.
  • Onboarding a new agent (or human) is one read, not an archaeology dig through chat logs.
  • Audit for free: who decided what, when, and why — verifiable with one hml verify.

Rule of thumb: the ledger read costs seconds and a few hundred tokens. Reconstructing a project's "why" from code costs an afternoon — and you still guess wrong half the time.

The full error vocabulary: E_STALE_STATE (lost the race), E_VALIDATION (strict schema — a typo'd key is rejected, not silently dropped), E_AUTHOR_PINNED (wrong author for this server), E_LOCKED (lock busy after ~13 s of retries), E_NOT_INITIALIZED (no genesis yet).

Crashes leave scars, not corruption

Kill the process mid-append and the file keeps a torn last line. The chain simply skips it — reported as a torn-line warning, forever — and the next commit terminates it with a newline. Nothing is ever truncated or hidden.

So — based on everything above, how do we get started?

Fifteen minutes, one project, every agent on the team.

1

Build HML once

Needs Node ≥ 20.

cd hml
npm install
npm run build
npm test
2

Create the ledger

In the project you want agents to share:

hml init --dir C:\path\to\project
3

Give everyone the same rules

Copy AGENTS.md, CLAUDE.md and GEMINI.md into the project root — every agent reads the same contract.

4

Connect each person's agent

.mcp.json for Claude Code, .gemini/settings.json for Gemini — each with its own --pin-author. Version events.jsonl and activeState.json in git.

5

Browser-only teammate?

The copy-paste loop (docs/WEB-SESSION-KIT.md):

hml read          → paste in chat
… agent works …
hml commit p.json → paste hash back
6

Trust, but verify

Sessions start with hml_read_state, end with hml_propose_handover — the handover only exists when the server returns a hash. Recheck the whole chain anytime:

hml verify
